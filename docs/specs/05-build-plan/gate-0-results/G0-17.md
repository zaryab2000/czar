## 2. A9-06 — the `eth_getLogs` block-range cap on `rpc.testnet.arc.io` — not run

**Not run: this environment's egress proxy refuses `rpc.testnet.arc.io`
with a `403` on the `CONNECT` tunnel.** Observed:

```sh
curl -sS -o /dev/null -w 'http_code=%{http_code}\n' --max-time 30 \
  -X POST -H 'content-type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}' \
  https://rpc.testnet.arc.io
```

```
curl: (56) CONNECT tunnel failed, response 403
http_code=000
```

The proxy's own record names the host and the reason:

```json
{ "ts": "…", "kind": "connect_rejected",
  "detail": "gateway answered 403 to CONNECT (policy denial or upstream failure)",
  "host": "rpc.testnet.arc.io:443" }
```

No workaround was attempted: TLS verification was not disabled, the proxy
was not unset, and no mirror or third-party RPC was substituted — a
third-party endpoint would measure that provider's cap, not Arc's, and would
be worthless as evidence here.

### The recorded value this check was to re-verify

`indexer.getLogsBlockRange = 9999` blocks, from fact **A9-06**: Arc's docs
publish `eth_getLogs` "Block range limit: 10,000 blocks" with error
`-32012`, and a load-balanced endpoint can return `-32014` near head. That
value is **unchanged** by this check and stays in force.

### Commands to run on an unrestricted network

```sh
RPC=https://rpc.testnet.arc.io

# 1. head
HEAD=$(curl -sS -X POST -H 'content-type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}' "$RPC" \
  | python3 -c 'import json,sys; print(int(json.load(sys.stdin)["result"],16))')

# 2. an inclusive span of exactly 10,000 blocks  (to = from + 9999)
TO=$HEAD; FROM=$((HEAD-9999))
curl -sS -X POST -H 'content-type: application/json' --data "$(printf \
  '{"jsonrpc":"2.0","id":2,"method":"eth_getLogs","params":[{"fromBlock":"0x%x","toBlock":"0x%x"}]}' \
  "$FROM" "$TO")" "$RPC"

# 3. an inclusive span of exactly 10,001 blocks  (to = from + 10000)
FROM=$((HEAD-10000))
curl -sS -X POST -H 'content-type: application/json' --data "$(printf \
  '{"jsonrpc":"2.0","id":3,"method":"eth_getLogs","params":[{"fromBlock":"0x%x","toBlock":"0x%x"}]}' \
  "$FROM" "$TO")" "$RPC"

# 4. the same two spans through the pinned toolchain, for the record
arc-cast logs --from-block $((HEAD-9999))  --to-block "$HEAD" --rpc-url "$RPC"
arc-cast logs --from-block $((HEAD-10000)) --to-block "$HEAD" --rpc-url "$RPC"
```

Run them read-only, with no key and no funds. Record the exact JSON-RPC
`error.code` and `error.message` of whichever call is refused, and the
`-32014` text if one appears near head.

### What each outcome means

| Outcome of steps 2 and 3 | Verdict to record | Effect |
|---|---|---|
| 10,000 blocks succeeds, 10,001 is refused with `-32012` | A9-06 **confirmed** as written | `indexer.getLogsBlockRange = 9999` stays; no SCR |
| Both succeed | A9-06 **changed**: the cap is higher than documented, or absent | `9999` is still safe; record the new ceiling, raise the page size only through an SCR on CZ-19 |
| 10,000 blocks is also refused | A9-06 **changed**: the cap is below 10,000, or counts the span exclusively | SCR on CZ-19 paging; `indexer.getLogsBlockRange` drops to the largest span that succeeds |
| A different error code than `-32012` | A9-06 **changed** in its error code | SCR on spec 01's RPC error table (`-32012` / `-32014` rows) and CZ-19's retry rule |

Note the ambiguity the commands above deliberately resolve: "10,000 blocks"
could count the span inclusively (`to − from + 1`) or as the difference
(`to − from`). Steps 2 and 3 pin the boundary either way. `9999` is below
the limit under both readings, which is why this check cannot block any
task that depends on it.
