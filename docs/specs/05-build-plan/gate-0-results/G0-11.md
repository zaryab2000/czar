- **Date:** 2026-11-05
- **Result:** three of the four items **confirmed**; the fourth, the
  plugin-bundled `.mcp.json` path, is **not run** here (the host skips
  plugin MCP servers in this environment). Two findings change what the
  plugin must ship (§2 and §6); no spec value changed.
- **Funds spent:** none. Nothing left the machine except two documentation

- **Source:** `claude` (Claude Code CLI) **2.1.318**, Linux 6.18.44, this
  repository's sandbox. Codex and Cursor are not installed, so the "repeat
  for Codex if installed" and the Cursor halves are not run.

## What was built, and where

A skeleton `czar-observer` plugin in a temporary folder outside the
repository and outside `plugins/claude-code/`:

```
<tmp>/czar-observer-skeleton/
├── .claude-plugin/plugin.json   # name, version, description, author, hooks, mcpServers
├── hooks/hooks.json             # 02 §8.2 shape, plus the two probes named below
├── .mcp.json                    # 02 mcp §5 shape, plus one probe env entry
├── skills/czar/SKILL.md
├── bin/czar-hook                # command-handler fallback (D46)
└── bin/czar-mcp                 # recording stdio MCP child
```

The hook listener for the run bound `127.0.0.1:18711` only, and was stopped
after the run. Two entries were added to the spec shapes purely as probes: a
`UserPromptSubmit` `http` handler (so a payload arrives without any tool
permission) and a `SessionStart` `command` handler with `async: true`.

## 2. New in 2.1.318: a separate "plugin directory" check block

The same run prints a block that `--strict` does **not** fail on:

```
× Found 2 problems the plugin directory refuses a submission for:
  > README.md: README missing (README_MISSING)
  > LICENSE: License missing (LICENSE_MISSING)
‼ Found 2 plugin directory warnings:
  > .claude-plugin/plugin.json icon: No icon (ICON_MISSING)
  > .claude-plugin/plugin.json privacyPolicyUrl: No privacy policy URL (PRIVACY_URL_MISSING)
These plugin directory checks do not change the result below.
```

```sh
claude plugin validate --strict --profile directory <tmp>/czar-observer-skeleton
# exit 1
```

So `--strict` alone still passes (fact E2-03 holds), but a second gate now
exists. The `PRIVACY_URL_MISSING` finding is raised **because** the plugin
declares an HTTP hook and an MCP server, which Czar's plugin always will.

- **Consequence for T-062:** the real plugin needs a `README.md`, a
  `LICENSE` (or `license` in `plugin.json`), an icon and a
  `privacyPolicyUrl` before it would pass `--profile directory`. Gate 0's
  pass rule asks only for `--strict`, which passes, so this is recorded, not
  treated as a failure.

## 3. The validator rejects the spec's unquoted `${CLAUDE_PLUGIN_ROOT}`

First run of the `command` handler, written the way spec 04
`local-observers-and-daemon.md` §5.1 names the file
(`"command": "${CLAUDE_PLUGIN_ROOT}/bin/czar-hook"`):

```
× Validation failed (--strict treats warnings as errors)   # exit 1
```

```json
{ "path": "hooks.SessionStart",
  "message": "Shell command uses ${CLAUDE_PLUGIN_ROOT} without quotes: ${CLAUDE_PLUGIN_ROOT}/bin/czar-hook. If the expanded path contains a space the command can split into several words and fail. Wrap the placeholder in double quotes, or use exec form: {\"command\": \"<executable>\", \"args\": [\"${CLAUDE_PLUGIN_ROOT}/...\"]}." }
```

After quoting (`"command": "\"${CLAUDE_PLUGIN_ROOT}/bin/czar-hook\""`) the
same command exits `0` with `√ Validation passed`.

- **Consequence for T-062:** the `command` fallback handler must quote the
  placeholder or use exec form. A spec note is proposed in §7.

## 4. `http` hook to a `127.0.0.1` listener (AR-18, D46) — confirmed

One session, with the plugin loaded for that session only:

```sh
printf '%s' 'Run the Glob tool once with the pattern "**" in the current directory, then reply with exactly DONE' |
  CZAR_HOOK_TOKEN=<dummy> CZAR_ENV_SUBST_PROBE=<dummy> \
  claude -p --model sonnet --plugin-dir <tmp>/czar-observer-skeleton --allowedTools=Glob
```

Two POSTs reached `http://127.0.0.1:18711/v1/hooks`, both
`content-type: application/json`:

| Handler | `hook_event_name` | `Authorization` received | Body keys |
|---|---|---|---|
| `UserPromptSubmit`, with `headers` + `allowedEnvVars` | `UserPromptSubmit` | `Bearer <the CZAR_HOOK_TOKEN value>` | `cwd`, `hook_event_name`, `permission_mode`, `prompt`, `prompt_id`, `scratchpad_dir`, `session_id`, `transcript_path` |
| `PostToolUse` (`*`), no `headers` block | `PostToolUse` | *absent* | `cwd`, `duration_ms`, `effort`, `hook_event_name`, `permission_mode`, `prompt_id`, `scratchpad_dir`, `session_id`, `tool_input`, `tool_name`, `tool_response`, `tool_use_id`, `transcript_path` |

- The `${CZAR_HOOK_TOKEN}` substitution in `headers` works, and
  `allowedEnvVars` is what lets it through.
- The field names spec 02 §8.2 maps are all present. One name not in the
  spec's list appears on `PostToolUse`: `effort`. It is not mapped, so it
  falls under "anything not listed is dropped at intake".
- No `PreToolUse` POST arrived, which is correct: the matcher is
  `Skill|mcp__.*|mcp__plugin_.*` and the tool used was `Glob`.

## 6. `.mcp.json` env substitution (AR-20) — substitution confirmed; the plugin path not run

### 6a. Substitution reaching the child — confirmed

The plugin-bundled `.mcp.json` child never started in the first run. The
reason is in this environment's own Claude Code configuration, visible in
the child's inherited environment:

```
CLAUDE_CODE_SKIP_PLUGIN_MCP_SERVERS=1
CLAUDE_CODE_SKIP_PLUGIN_MCP_SERVERS_EXCEPT=documents
```

So the substitution was proved instead through an MCP config file carrying
the identical `env` block, which the host does load here:

```sh
printf '%s' 'Reply with exactly DONE' |
  CZAR_ENV_SUBST_PROBE=g0-11-env-subst-value \
  claude -p --model sonnet --mcp-config <tmp>/mcp-config-probe.json --strict-mcp-config
```

`env` in that file: `{"CZAR_DEVICE_TOKEN": "${CZAR_ENV_SUBST_PROBE}",
"CZAR_API_URL": "http://localhost"}`. The stdio child's own environment:

| Key | Value the child saw |
|---|---|
| `CZAR_DEVICE_TOKEN` | `g0-11-env-subst-value` — the `${…}` was substituted from the host's process environment |
| `CZAR_API_URL` | `http://localhost` — literal, passed through |

So `${VAR}` in an MCP server's `env` is substituted by the host and reaches
the stdio child. The child also inherits the host's own environment, which
in this sandbox includes the account's e-mail address and session tokens;
those are deliberately not reproduced here, and `czar-mcp` must read only
the two keys 02 mcp §5 names.

### 6b. `${CLAUDE_PLUGIN_OPTION_DEVICE_TOKEN}` — not run

The form spec 02 mcp §5 actually ships
(`"CZAR_DEVICE_TOKEN": "${CLAUDE_PLUGIN_OPTION_DEVICE_TOKEN}"` inside a
plugin's `.mcp.json`) could not be exercised, because it needs the plugin
MCP path that this environment skips. Clearing the two flags above for one
session was refused by this environment's permission layer, and was not
worked around.

- **To run elsewhere**, on a host that does not set those flags:

  ```sh
  claude plugin install <plugin>             # or: claude -p --plugin-dir <plugin>
  claude plugin configure czar-observer --values-stdin   # set device_token
  # then confirm the child's own env holds the option's value, not the literal "${…}"
  ```

- **What would change the record:** if the child sees the literal
  `${CLAUDE_PLUGIN_OPTION_DEVICE_TOKEN}`, or an empty value when the option
  is unset, then `plugin.json` must declare the option under `userConfig`
  and CZ-09 must fail closed on an unsubstituted value. An SCR on 02 mcp §5
  would follow. If the child sees the configured value, 02 mcp §5 stands as
  written.

## 7. MCP protocol revision each host negotiates (D3 GAP) — confirmed for Claude Code

Recorded from the stdio child's own JSON-RPC frames, in order:

| # | Direction | Frame |
|---:|---|---|
| 1 | client → server | `server/discover`, `id: "server-discover-probe-1"`, `params._meta` = `{"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientInfo": {"name": "claude-code", "version": "2.1.318", …}, "io.modelcontextprotocol/clientCapabilities": {"roots": {"listChanged": true}, "elicitation": {"form": {}, "url": {}}}}` |
| 2 | server → client | `-32601 method not found` |
| 3 | client → server | `initialize`, `id: 0`, `params.protocolVersion: "2025-11-25"`, `capabilities: {"roots": {"listChanged": true}, "elicitation": {"form": {}, "url": {}}}` |
| 4 | server → client | `result.protocolVersion: "2025-11-25"` |
| 5 | client → server | `notifications/initialized` |
| 6 | client → server | `tools/list` |

So Claude Code 2.1.318 **probes the current era first** with
`server/discover` carrying `_meta["io.modelcontextprotocol/protocolVersion"]
= "2026-07-28"`, and on `-32601` falls back to the legacy `initialize`
handshake at **`2025-11-25`**. Both paths of 02 mcp §6 are therefore needed,
exactly as that section says, and the detection rule in §6 ("if the first
message is `initialize` → legacy") must tolerate a `server/discover` arriving
*before* `initialize` in the same session.

A second run, in which the child answered the probe, ran the legacy path as
well:

| # | Frame |
|---:|---|
| 1 | `server/discover`, `_meta` protocol version `2026-07-28` |
| 2 | server answered `{"resultType": "discover", "tools": [], "serverInfo": {…}}` |
| 3 | `initialize` with `protocolVersion: "2025-11-25"` — still sent |

- **Caveat on that second run:** the `server/discover` **result shape is not
  given anywhere in Czar's specs**, so the answer above is a guess. The host
  may have fallen back because the shape was wrong rather than by policy.
  Read it as "answering the probe with that shape did not keep the session on
  `2026-07-28`", not as "answering the probe never does".
- **Codex:** not installed. Not run.

## Spec problems found (for the architect to file)

1. **`czarHookVersion` cannot be set by an `http` handler.** Spec 04
   `local-observers-and-daemon.md` §4 says the daemon receives "the raw hook
   JSON plus `{"czarHookVersion": 1}`". Observed: the `http` handler posts
   the host's payload unchanged; there is no field to add one. Either the
   daemon must treat a missing `czarHookVersion` as version 1, or the field
   must move to a header, or only the `command` handler may add it.
2. **`Authorization` on the `PostToolUse` handler.** Spec 04 §4 says every
   POST carries `Authorization: Bearer <K16>`, but the `PostToolUse` handler
   in 02 §8.2's example has no `headers` block, and the POST arrived with no
   `Authorization`. Observed above. Every `http` handler needs the `headers`
   and `allowedEnvVars` pair, or the daemon must accept an unauthenticated
   POST on `127.0.0.1`, which it should not.
3. **Quoting of `${CLAUDE_PLUGIN_ROOT}`** in the `command` fallback handler,
   per §3 above.
4. **`server/discover` result shape** is referenced by 02 mcp §6 ("the
   server MUST implement `server/discover`") but never defined, which is why
   §7's second run cannot be conclusive.
5. **`hostVersion` for Claude Code** has no source on 2.1.318 (§5).
